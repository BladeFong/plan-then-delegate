# Plan-Then-Delegate

## 核心原则

主代理只做三件事：**划分任务 / 对齐方案** + **主持审查与返工** + **整理文档**。具体代码改动一律通过 Agent 工具分发给子代理，**串行、前台、逐任务闭环**。

主代理**不**：
- 给子代理的落实细节提意见
- 自己接手问题和下场写代码改文件（除非用户明确要求"这次你直接改"，或者你已有所需的上下文，告知用户征得同意）
- 自己看子代理处理问题后的log（应该把用户反馈的log文件路径直接丢给子代理让它自己看）
- 一条消息里并发起多个子代理
- 用 `run_in_background=true` 起做写操作的子代理
- 把同一个问题拆给多个子代理
- 让子代理来写文档
- 自己跑编译 / 测试验证（编译归实现子代理，测试归测试子代理；主代理不关心命令、不重复跑）
- 要求子代理跑项目全量测试
- 替用户回答子代理的「待确认问题」，或替子代理补充决策信息
- 在分发前自己逐文件排查根因细节 —— 主代理保持总任务设计与规划层面的上下文干净，落地细节上下文存留在固定的子代理里

## 工作流

整体阶段（每个阶段详见对应小节）：

1. **任务划分 / 方案对齐**（第 1 节）：主代理承接上游规划或对齐目标与边界，与用户确认；不做细节深挖
2. **串行分发**（第 2 节）：主代理串行前台调起实现子代理，一次一个任务；分发前与用户确认 R / V 两个开关
3. **任务闭环**（第 3 节）：每个任务依次 F 实现 → R 审查（启用时）→ V 测试（该任务需要时）→ 完整闭环后才进入下一个任务
4. **统一整理文档**（第 4 节）：主代理把所有改动整合到项目约定的汇总 / 长期文档；不跑编译

### 1. 任务划分 / 方案对齐

主代理保持"总任务设计与规划"层面的上下文干净：**规划与查证尽量在上游完成**（brainstorming / writing-plans 等技能的产物直接承接），主代理不做逐文件根因深挖——落地细节上下文存留在固定的子代理里，这正是本技能分层的意义。

**单问题**：与用户对齐"现象 / 目标 / 边界 / 偏好"即可；根因定位与细节分析由实现子代理先做（见第 2 节 prompt 与 agent-impl.md「先分析，后动手」），分析结论与目标冲突时以「待确认问题」转回来。上游已查证过根因的，把结论随 prompt 下发。

**多任务**（问题可按模块拆分，或用户直接给出一批需求）：按**模块耦合度和建议推进顺序**划分任务清单，呈现给用户确认后再分发。划分要求：

- 覆盖完整、不偷懒遗漏细节：边缘改动、连带影响（调用方、配置、常量）逐任务核对归位
- 每个任务写清：目标 / 涉及模块与文件线索 / 边界（不做什么）/ 验收标准
- 任务内的细节分析下沉给实现子代理：主代理给目标和边界，不替子代理做逐文件深挖

不确定的点不要替用户拍板，也不能把猜测当作确定的方案擅自推进。用户可能对方案细节有偏好（命名、风格、范围），这一步把它们对齐清楚。

### 2. 串行分发子代理

**一次只起一个子代理**：在同一条主代理消息里只调一次 Agent 工具，等返回后再起下一个。

**保存 agent_id**：Agent 工具返回结果中包含 `agent_id`。主代理给每个子代理起逻辑名（如 F1/F2/V1/R1），记录 逻辑名 ↔ agent_id 对应关系。流程后续需用 `SendMessage(to: agent_id)` 续接同一个子代理——agent_id 跨"已退出"状态仍然有效，续接不丢上下文；冷启动会丢上下文、token 翻倍。

**续接边界**：只续接**本会话内** spawn 的子代理。Fork 出来的会话、客户端重启后的会话，运行时注册表里没有旧代理（SendMessage 会报 No active task 类错误），此时不要反复尝试续接，直接冷启动新子代理接力。

**前台运行**：`run_in_background` 留空或显式 false。只有任务里完全没有 Write/Edit/Bash 写文件动作（纯查询）时才考虑后台。

**子代理类型**：落盘类任务用 `subagent_type: general-purpose`（工具齐全，能 Read references、能自跑编译）；只读的探索类子代理（如 Explore）不承担落盘任务。

**分发前确认两个开关**（一次问完；项目记忆里声明默认的按声明执行、不再问）：

- 是否启用审查循环（R）
- 任务闭环是否含测试循环（V）

**实现子代理 prompt 模板**（必填字段不可省，可选字段按需）：

```
[可选，冷启动实现子代理时需要]
你是 plan-then-delegate 的「实现代理 F」。请先用 Read 读取执行规则：
~/.zcode/skills/plan-then-delegate/references/agent-impl.md
读取失败立即返回固定文案「references 读取失败」并停止。

## 任务背景  [必填]
<一句话说明问题 / 现象>

## 根因 / 成因线索  [可选]
<主代理或上游规划已查证的填这里；未查证则留空，由 F 自行分析>

## 已确认方案  [必填]
- 目标：<要达成什么>
- 边界：<不做什么；涉及模块 / 文件线索>
- 验收标准：<怎样算完成>
- 命名 / 风格：<用户特别强调的偏好；项目级规范从 CLAUDE.md / AGENTS.md 自取>

## 特殊编译命令  [可选]
<覆盖默认；通常不填>
```

上游已确定具体改法的，把改动文件 / 关键代码写进「已确认方案」并填实「根因 / 成因线索」；未确定改法的留在目标层，细节分析由 F 完成。

冷启动 prompt 中的 references 路径以本机实际安装路径为准（用户级安装默认 `~/.zcode/skills/plan-then-delegate/`）。

需要让实现子代理返工时，优先用 `SendMessage(to: agent_id)` 续接原子代理发返工指令，prompt 只包含最新状况；续接失败（报 No active task / 找不到代理类错误）时，冷启动一个新的子代理接力，prompt 带全任务背景与此前结论摘要。

一个问题对应一个实现子代理。
**禁止**存在处理过问题相同模块的实现子代理时，因为用户的提问有部份不确定同属一个模块，就偷懒打包，暴力新建子代理处理。
如果分析问题后发现，是之前某一个流程处理的后续或者同一模块（"上次改了 A 之后又发现 B，或者没完全改好"），同时主代理工具列表中存在 `SendMessage`，则用 `SendMessage` 分发给处理那个流程的实现子代理继续处理。
如果同一问题涉及多个文件 / 多步，全部在同一个实现子代理里完成，不要拆。
如果多个问题集中在同一模块或关联性大，不涉及有不同实现子代理处理过的部分，可以合并成一次修改任务。

### 3. 任务闭环（F → R → V）

每个任务依次经过：**F 实现 → R 审查（启用时）→ V 测试（该任务需要时）**，全部闭环后才进入下一个任务；任何时候只有一条流水线在跑。

**F 返回后**：主代理只做轻量校验（看反馈里有没有偏离方案、有没有遗留点）。**不**重新读 F 改过的文件来"验证"——F 的 Edit/Write 失败会直接报错；可做的是必要时浏览关键改动确认理解。

**待确认问题转述**：任何子代理返回中含「## 待确认问题」时，主代理原样转述给用户——不替用户回答、不改写或增删选项、不替子代理补充信息；拿到答复后 `SendMessage(to: agent_id)` 回原子代理继续。

**R 审查（启用时，与 F 配对）**：F 通过轻量校验后，主代理冷启动**配对的审查代理 R**（`subagent_type: general-purpose`，前台；执行规则与冷启动模板见 [`references/agent-review.md`](references/agent-review.md)）——R 自行用 Skill 工具加载 `code-review-excellence`，以与实现同样严格的标准只读审查本轮改动。R 返回：

- **通过** → 进入本任务的 V 环节（未启用测试时任务直接闭环）
- **不通过** → 主代理主持返工：把 R 的问题清单**原样**发给对应 F（`SendMessage` 续接），F 返工返回后交原 R 复审；两轮返工仍不通过，停下向用户汇报分歧点，由用户裁决
- 返工期间主代理不下场改代码；R 只读不改码，改动一律由原 F 做

**V 测试（该任务判定需要测试时，与 F 配对）**：R 通过后，主代理判断该任务改动是否需要测试；需要则读取 [`references/test-loop.md`](references/test-loop.md) 执行 F↔V 直连的修复-复验循环（V 既评估又动手写测试；发现的业务代码问题由 V 直接 `SendMessage` 发给 F，F 修复后回 V 复验）。无需测试的任务直接闭环。

**回审兜底**（本轮启用过审查循环时）：V 循环里 F 的业务代码修复若属较大结构改动（多函数联动、新增公共接口、调用链调整等），发**原 R**（`SendMessage` 续接）增量复审，通过才算该任务闭环；小修由测试验证兜底。

**跨任务回归兜底**：后续任务的改动波及已闭环任务的模块时，主代理可 `SendMessage` 原 V 复验相关测试；续接失败则按第 2 节的接力规则冷启动新 V。

### 4. 统一整理文档

所有任务（含可选的审查、测试环节）都闭环后，主代理询问用户，是否要把所有改动整合写到项目约定的汇总 / 长期文档里：
- 文档结构由项目 CLAUDE.md / AGENTS.md / README / 既有文档惯例决定；主代理顺着既有结构写，不强加形态
- **不重复跑编译 / 测试**——子代理已经自跑通过；主代理只整合内容
- 走过审查 / 测试环节的，把审查结论、测试结果一并记录

## 诊断信号

### 「references 读取失败」

主代理读不到 `references/test-loop.md` / `references/agent-review.md`，或子代理读不到执行规则文件（`references/` 下的 `agent-impl.md`、`agent-test.md` 或 `agent-review.md`）。通常因为 skill 没完整安装：只链了 SKILL.md 单文件，没把 references/ 目录一起带过来。

处理：告知用户「plan-then-delegate skill 未完整安装，references 目录缺失」，让用户修复后重试。

### 子代理权限被拒

子代理返回里 Write / Edit / Bash 被权限拒绝（permission denied 类文案）。处理顺序：

1. 检查是否并行 spawn 或 `run_in_background=true` → 改串行、前台
2. 检查当前会话权限模式是否允许子代理写操作；必要时请用户调整权限模式或批准对应工具
3. 仍失败：向用户说明，本次例外由主代理直接落盘，或等用户处理权限后重试

### 子代理续接失败

`SendMessage` 报 No active task / 找不到代理类错误，说明目标不在本会话运行时注册表（跨 Fork、客户端重启、或 ID 有误）。处理：不要反复重试续接，冷启动一个新的子代理接力，prompt 带全任务背景与此前结论摘要，并说明当前进行到哪一步。

## 何时不用本技能

- 单个简单改动（一行 typo、一个变量重命名）：主代理直接改更快
- 用户明确说"这次你直接改"："对齐方案 → 主代理落盘"
- 纯研究 / 探索任务（没有代码改动）：用 explore / general-purpose 子代理即可，不需要本技能的角色分工
