# Plan-Then-Delegate

## 核心原则

主代理只做两件事：**和用户对齐方案** + **整理文档**。具体代码改动一律通过 Agent 工具分发给子代理，**串行、前台**。

主代理**不**：
- 不给子代理的落实细节提意见
- 自己下场写代码改文件（除非用户明确要求"这次你直接改"）
- 不自己看子代理处理问题后的log，把用户反馈的log文件路径直接丢给子代理让它自己看
- 一条消息里并发起多个子代理
- 用 `run_in_background=true` 起做写操作的子代理
- 把同一个问题拆给多个子代理
- 让子代理来写文档
- 自己跑编译 / 测试验证（编译归实现子代理，测试归测试子代理；主代理不关心命令、不重复跑）

## 工作流

整体阶段（每个阶段详见对应小节）：

1. **方案对齐**（第 1 节）：主代理排查根因，与用户确认方案
2. **串行分发**（第 2 节）：主代理串行前台调起实现子代理，一次一个，每个实现子代理落盘一个问题后返回修改要点
3. **收集反馈**（第 3 节）：主代理对每个实现子代理返回做轻量校验，校验通过再起下一个
4. **补充测试循环**（第 4 节，可选）：所有实现子代理完成后、且 `SendMessage` 工具可用时，主代理询问用户是否补充测试；同意则进入测试代理 ↔ 实现代理 轮流跑的循环，直到全绿
5. **统一整理文档**（第 5 节）：主代理把所有改动整合到项目约定的汇总 / 长期文档；不跑编译

### 1. 排查与方案对齐

主代理通过 Read / Grep / Glob / 必要的 WebSearch 等只读工具排查根因，把问题的"根因 + 拟定方案"用 AskUserQuestion 或自由回复呈现给用户，**等用户明确确认**后再分发。

不确定的点不要替用户拍板，也不要把猜测当作确定的方案擅自推进。用户可能对方案细节有偏好（命名、风格、范围），这一步把它们对齐清楚。

### 2. 串行分发子代理

**一次只起一个子代理**：在同一条主代理消息里只调一次 Agent 工具，等返回后再起下一个。

**保存 agent_id**：Agent 工具调用时必须传 `name` 参数（如 `F1`/`F2`/`V1`），返回结果中包含 `agent_id`，主代理记录每个子代理的 name ↔ agent_id 对应关系。流程后续需用 `SendMessage(to: agent_id)` 续接同一个子代理——agent_id 跨"已退出"状态仍然有效；冷启动会丢上下文、token 翻倍。

**前台运行**：`run_in_background` 留空或显式 false。只有任务里完全没有 Write/Edit/Bash 写文件动作（纯查询）时才考虑后台。

**实现子代理 prompt 模板**（必填字段不可省，可选字段按需）：

```
[可选，冷启动实现子代理时需要]
你是 plan-then-delegate 的「实现代理 F」。请先用 Read 读取执行规则：
~/.claude/skills/plan-then-delegate/references/agent-impl.md
读取失败立即返回固定文案「references 读取失败」并停止。

## 任务背景  [必填]
<一句话说明问题>

## 根因  [必填]
<主代理已排查的根因>

## 已确认方案  [必填]
- 改动文件：<file_path>
- 关键代码 / 函数：<片段或定义>
- 命名 / 风格：<用户特别强调的偏好；项目级规范从 CLAUDE.md 自取>

## 特殊编译命令  [可选]
<覆盖默认；通常不填>
```

需要让实现子代理返工时，如果因为主代理工具列表中不存在 `SendMessage` 或其他原因，无法让原子代理继续，需要冷启动一个新的子代理接力。
测试循环场景的 SendMessage 模板（修复 F、复验 V）见 [`references/test-loop.md`](references/test-loop.md)。

一个问题对应一个实现子代理。
如果同一问题涉及多个文件 / 多步，全部在同一个实现子代理里完成，不要拆。
如果多个问题集中在同一模块或关联性大，合并成一次修改任务。
如果分析问题后发现，是之前某一个流程处理的后续或者同一模块（"上次改了 A 之后又发现 B，或者没完全改好"），同时主代理工具列表中存在 `SendMessage` ，则分发给处理那个流程的实现子代理继续处理。

### 3. 收集反馈并继续

实现子代理返回后，主代理只做轻量校验（看反馈里有没有偏离方案、有没有遗留点）。**不**重新读实现子代理改过的文件来"验证"——实现子代理 Edit/Write 失败会直接报错，没必要主代理重复确认；可以做的是必要时浏览关键改动确认理解。

如果反馈正常，起下一个实现子代理处理下一个问题；否则澄清问题，必要时向用户提问，然后调整让 prompt 只包含最新状况，让实现子代理返工，实现子代理返回结果后，重新进入第 3 节；每次返工阶段结束，确认一下当前流程。

### 4. 补充测试循环（可选）

**触发条件**：所有实现子代理完成报告后，**且主代理工具列表中存在 `SendMessage` 工具**。主代理主动询问用户："是否要进行补充测试？" 用户同意才进入本流程；用户不要、或 SendMessage 不可用，直接跳到第 5 节。

**核心结构**：每个实现代理 F 配一个测试代理 V（一一对应、严格串行，任何时候只有一对在跑）。V 既评估又动手——需要调整 / 新增的测试由 V 自己改 / 写；发现的业务代码问题反馈给主代理，由主代理 `SendMessage` 派回 F 修复，然后再让 V 复验。每对完整闭环（含修复迭代）后才进入下一对。

**详细执行规则、SendMessage 用法、V 模板、F 模板**：见 [`references/test-loop.md`](references/test-loop.md)。

### 5. 统一整理文档

所有子代理（含可选的测试循环）都跑完后，主代理 AskUserQuestion 询问用户，是否要把所有改动整合写到项目约定的汇总 / 长期文档里：
- 文档结构由项目 CLAUDE.md / README / 既有文档惯例决定；主代理顺着既有结构写，不强加形态
- **不重复跑编译 / 测试**——子代理已经自跑通过；主代理只整合内容
- 如果走了第 4 节测试循环，把测试结果一并记录

## 诊断信号

### 「references 读取失败」

第 4 节读取不到 `references/test-loop.md` ，子代理读不到执行规则文件（`references/` 下的 `agent-impl.md` 或 `agent-test.md`）。通常因为 skill 没完整安装：只链了 SKILL.md 单文件，没把 references/ 目录一起带过来。

处理：告知用户「plan-then-delegate skill 未完整安装，references 目录缺失」，让用户修复后重试。

## 何时不用本技能

- 单个简单改动（一行 typo、一个变量重命名）：主代理直接改更快
- 用户明确说"这次你直接改"："对齐方案 → 主代理落盘"
- 纯研究 / 探索任务（没有代码改动）：用 explore / general-purpose 子代理即可，不需要本技能的角色分工
