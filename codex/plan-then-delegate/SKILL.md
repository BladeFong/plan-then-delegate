# Plan-Then-Delegate

## 核心原则

主代理只做三件事：**划分任务 / 对齐方案** + **主持审查与返工** + **整理文档**。具体代码改动一律通过 Agent 工具分发给子代理，**串行、前台**。

主代理**不**：
- 给子代理的落实细节提意见
- 自己接手问题和下场写代码改文件（除非用户明确要求"这次你直接改"，或者你已有所需的上下文，告知用户征得同意）
- 自己看子代理处理问题后的log（应该把用户反馈的log文件路径直接丢给子代理让它自己看）
- 一条消息里并发起多个子代理
- 用 `run_in_background=true` 起做写操作的子代理
- 把同一个问题拆给多个子代理
- 让子代理来写文档
- 自己跑编译 / 测试验证（编译归实现子代理，测试归测试子代理；主代理不关心命令、不重复跑）
- 要求子代理跑项目全量测试
- 替用户回答子代理的「待确认问题」，或替子代理补充决策信息

## 工作流

整体阶段（每个阶段详见对应小节）：

1. **任务划分 / 方案对齐**（第 1 节）：主代理排查根因或划分任务清单，与用户确认
2. **串行分发**（第 2 节）：主代理串行前台调起实现子代理，一次一个，每个实现子代理落盘一个任务后返回修改要点
3. **收集反馈**（第 3 节）：主代理对每个返回做轻量校验；启用审查循环时交配对审查子代理严格审查、主持返工；转述「待确认问题」
4. **补充测试循环**（第 4 节，可选）：所有实现子代理完成后、且 `SendMessage` 工具可用时，主代理对需要测试的改动询问用户是否补充测试；同意则进入测试代理 ↔ 实现代理直连的修复-复验循环
5. **统一整理文档**（第 5 节）：主代理把所有改动整合到项目约定的汇总 / 长期文档；不跑编译

### 1. 任务划分 / 方案对齐

**单问题**：主代理通过 Read / Grep / Glob / 必要的 WebSearch 等只读工具排查根因，把问题的"根因 + 拟定方案"用 AskUserQuestion 或自由回复呈现给用户，**等用户明确确认**后再分发。

**多任务**（问题可按模块拆分，或用户直接给出一批需求）：主代理按**模块耦合度和建议推进顺序**划分任务清单，呈现给用户确认后再分发。划分要求：

- 覆盖完整、不偷懒遗漏细节：边缘改动、连带影响（调用方、配置、常量）逐任务核对归位
- 每个任务写清：目标 / 涉及模块与文件线索 / 边界（不做什么）/ 验收标准
- **任务内的细节分析下沉给实现子代理**：主代理给目标和边界，不替子代理做逐文件深挖 —— 这正是把主代理上下文留给全局判断与审查主持的交换；子代理分析结论与已确认目标冲突时，会以「待确认问题」转回来（见第 3 节）

不确定的点不要替用户拍板，也不能把猜测当作确定的方案擅自推进，更不能把未经用户确认的选项当作方案推进。用户可能对方案细节有偏好（命名、风格、范围），这一步把它们对齐清楚。

### 2. 串行分发子代理

**一次只起一个子代理**：在同一条主代理消息里只调一次 Agent 工具，等返回后再起下一个。

**保存 agent_id**：Agent 工具返回结果中包含 `agent_id`。主代理给每个子代理起逻辑名（如 F1/F2/V1/R1），记录 逻辑名 ↔ agent_id 对应关系。流程后续需用 `SendMessage(to: agent_id)` 续接同一个子代理——agent_id 跨"已退出"状态仍然有效，续接不丢上下文；冷启动会丢上下文、token 翻倍。

**前台运行**：`run_in_background` 留空或显式 false。只有任务里完全没有 Write/Edit/Bash 写文件动作（纯查询）时才考虑后台。

**子代理类型**：落盘类任务用 `subagent_type: general-purpose`（工具齐全，能 Read references、能自跑编译）；只读的探索类子代理（如 Explore）不承担落盘任务。

**实现子代理 prompt 模板**（必填字段不可省，可选字段按需）：

```
[可选，冷启动实现子代理时需要]
你是 plan-then-delegate 的「实现代理 F」。请先用 Read 读取执行规则：
~/.zcode/skills/plan-then-delegate/references/agent-impl.md
读取失败立即返回固定文案「references 读取失败」并停止。

## 任务背景  [必填]
<一句话说明问题>

## 根因  [必填]
<主代理已排查的根因>

## 已确认方案  [必填]
- 改动文件：<file_path>
- 关键代码 / 函数：<片段或定义>
- 命名 / 风格：<用户特别强调的偏好；项目级规范从 CLAUDE.md / AGENTS.md 自取>

## 特殊编译命令  [可选]
<覆盖默认；通常不填>
```

多任务划分模式下：「根因」填该任务的背景与成因线索，「已确认方案」填用户确认的任务条目（目标 / 边界 / 验收标准），并在 prompt 末尾加一行「细节分析由你完成：先自行分析相关文件与调用链，再动手」。

冷启动 prompt 中的 references 路径以本机实际安装路径为准（用户级安装默认 `~/.zcode/skills/plan-then-delegate/`）。

需要让实现子代理返工时，优先用 `SendMessage(to: agent_id)` 续接原子代理发返工指令，prompt 只包含最新状况；仅当主代理工具列表中没有 `SendMessage` 时，才冷启动一个新的子代理接力。

一个问题对应一个实现子代理。
**禁止**存在处理过问题相同模块的实现子代理时，因为用户的提问有部份不确定同属一个模块，就偷懒打包，暴力新建子代理处理。
如果分析问题后发现，是之前某一个流程处理的后续或者同一模块（"上次改了 A 之后又发现 B，或者没完全改好"），同时主代理工具列表中存在 `SendMessage`，则用 `SendMessage` 分发给处理那个流程的实现子代理继续处理。
如果同一问题涉及多个文件 / 多步，全部在同一个实现子代理里完成，不要拆。
如果多个问题集中在同一模块或关联性大，不涉及有不同实现子代理处理过的部分，可以合并成一次修改任务。

### 3. 收集反馈（含审查循环）

实现子代理返回后，主代理只做轻量校验（看反馈里有没有偏离方案、有没有遗留点）。**不**重新读实现子代理改过的文件来"验证"——实现子代理 Edit/Write 失败会直接报错，没必要主代理重复确认；可以做的是必要时浏览关键改动确认理解。

**待确认问题转述**：任何子代理返回中含「## 待确认问题」时，主代理原样转述给用户——不替用户回答、不改写或增删选项、不替子代理补充信息；拿到答复后 `SendMessage` 回原子代理继续。

**审查循环（可选、配对、严格串行）**：分发前主代理询问用户一次是否启用（项目记忆里声明默认开启 / 关闭的，按声明执行、不再问）。启用时，每个实现子代理通过轻量校验后，主代理冷启动**配对的审查子代理 R**（`subagent_type: general-purpose`，前台；执行规则与冷启动模板见 [`references/agent-review.md`](references/agent-review.md)）——R 自行用 Skill 工具加载 `code-review-excellence`，以与实现同样严格的标准只读审查本轮改动。审查循环同样严格串行：一对 F-R（含返工复审）完整闭环后，才进入下一个任务。R 返回：

- **通过** → 起下一个任务
- **不通过** → 主代理主持返工：把 R 的问题清单**原样**发给对应实现子代理（`SendMessage` 续接），实现子代理返工返回后交原 R 复审（R 已有上下文，不冷启动）；两轮返工仍不通过，停下向用户汇报分歧点，由用户裁决
- 返工期间主代理不下场改代码；R 只读不改码，改动一律由原实现子代理做

未启用审查循环时：反馈正常就起下一个实现子代理处理下一个问题；否则澄清问题，必要时向用户提问，然后让实现子代理返工，实现子代理返回结果后，重新进入本节。每次返工阶段结束，确认一下当前流程。

### 4. 补充测试循环（可选）

**触发条件**：所有实现子代理完成报告后，**且主代理工具列表中存在 `SendMessage` 工具**。缺任一 → 直接跳到第 5 节。

主代理**先**逐 F 判断改动是否有必要测试。**全部 F 无需测试 → 直接跳到第 5 节**，不问用户、不进测试循环。

至少一个 F 需要测试时，向用户呈现待测列表并询问。用户不同意 → 第 5 节；用户同意 → 使用独立 V 对改动跑相关测试（含跨模块影响）以确认有无回归。**禁止代修问题或改测试**，**仅当存在需要测试的 F 时**，才读取 [`references/test-loop.md`](references/test-loop.md) 获取 F-V 循环执行细节。

**核心结构**：每个需要测试的 F 配一个 V（一一对应、严格串行，任何时候只有一对在跑）。V 既评估又动手——需要调整 / 新增的测试由 V 自己改 / 写；发现的业务代码问题由 V 直接 `SendMessage` 发给 F（F 收到消息自动续跑），F 修复后直接回 V 复验。主代理不参与中继，只等 V 的最终报告。每对完整闭环（含修复迭代）后才进入下一对。

**回审兜底**（本轮启用过审查循环时）：某对 F-V 闭环里，F 的业务代码修复若属较大结构改动（多函数联动、新增公共接口、调用链调整等），主代理在该对闭环后把修复要点发**原审查代理 R**（`SendMessage` 续接）增量复审，通过才算该对真正闭环；小修由测试验证兜底，不回审。

### 5. 统一整理文档

所有子代理（含可选的审查、测试循环）都跑完后，主代理询问用户，是否要把所有改动整合写到项目约定的汇总 / 长期文档里：
- 文档结构由项目 CLAUDE.md / AGENTS.md / README / 既有文档惯例决定；主代理顺着既有结构写，不强加形态
- **不重复跑编译 / 测试**——子代理已经自跑通过；主代理只整合内容
- 如果走了审查循环 / 测试循环，把审查结论、测试结果一并记录

## 诊断信号

### 「references 读取失败」

主代理读不到 `references/test-loop.md` / `references/agent-review.md`，或子代理读不到执行规则文件（`references/` 下的 `agent-impl.md`、`agent-test.md` 或 `agent-review.md`）。通常因为 skill 没完整安装：只链了 SKILL.md 单文件，没把 references/ 目录一起带过来。

处理：告知用户「plan-then-delegate skill 未完整安装，references 目录缺失」，让用户修复后重试。

### 子代理权限被拒

子代理返回里 Write / Edit / Bash 被权限拒绝（permission denied 类文案）。处理顺序：

1. 检查是否并行 spawn 或 `run_in_background=true` → 改串行、前台
2. 检查当前会话权限模式是否允许子代理写操作；必要时请用户调整权限模式或批准对应工具
3. 仍失败：向用户说明，本次例外由主代理直接落盘，或等用户处理权限后重试

## 何时不用本技能

- 单个简单改动（一行 typo、一个变量重命名）：主代理直接改更快
- 用户明确说"这次你直接改"："对齐方案 → 主代理落盘"
- 纯研究 / 探索任务（没有代码改动）：用 explore / general-purpose 子代理即可，不需要本技能的角色分工
