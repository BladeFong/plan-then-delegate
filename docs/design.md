# Plan-Then-Delegate 设计文档

## 问题陈述

多步骤编码任务由主代理一手包办时，存在两个问题：

1. **上下文挤占**：主代理把上下文耗在具体改动细节（读文件、写代码、改 import 顺序）上，挤掉对方案的判断、跨文件一致性审视和文档整理能力。
2. **Claude Code 父子代理权限传递 bug**：尝试并行 / 后台分发子代理时，会命中已知 bug（详见下文），子代理的 Write/Edit/Bash 被拒，整个分发链路打断。

## 设计目标

- 主代理保持在"方案 / 整理"层面，不下场改代码（除非用户明确要求）
- 通过子代理承担具体改动，保持主代理上下文清爽
- 工作流自然规避 Claude Code 已知的并行 / 后台权限传递 bug
- 多个独立问题串行依次处理，避免互相干扰
- 编译 / 测试验证职责下沉到子代理，主代理不重复跑
- 双平台支持（Claude Code / Codex），核心工作流一致，平台差异隔离在工具名和通信机制层

## 架构

整体流程分 5 阶段（详见各平台 SKILL.md）：

1. **方案对齐**：主代理用只读工具排查根因，与用户对齐方案
2. **串行分发**：主代理一条消息只起一个子代理；每个子代理输入"背景 + 根因 + 已确认方案 + 范围约束"，输出"修改清单 + 编译验证结果 + 偏离方案的地方 + 遗留点"
3. **收集反馈**：主代理对每个子代理返回做轻量校验，校验通过再起下一个
4. **补充测试循环**：主代理询问用户是否补充测试；同意后对每个实现代理配一个测试代理评估并补 / 调测试，发现的业务代码问题主代理派回对应实现代理修，每对完整闭环后才进入下一对
5. **统一整理文档**：主代理把所有改动整合到项目约定的汇总 / 长期文档；不重复跑编译 / 测试

## 关键决策

### 1. 串行而非并行

**根因**：[anthropics/claude-code#57037](https://github.com/anthropics/claude-code/issues/57037) — 一条消息里并行 spawn 多个 Agent 时，每个子代理遭遇权限级联失败（首个 Bash 通常成功，后续 Write/Edit 全被拒）；单独顺序 spawn 同一个子代理却成功。

Codex 不存在此 bug，但串行仍然保留——并行会增加用户管理难度，且本技能定位为轻量方案，串行的简单性优于并行的吞吐量。

**决策**：主代理一条消息里只起一个子代理，等返回后再起下一个。

### 2. 前台而非后台

**根因**：[#34095](https://github.com/anthropics/claude-code/issues/34095) — 背景子代理（`run_in_background=true`）的 Write/Edit 被静默自动拒，即使父会话已批准相同工具，权限不传递。

**决策**：默认前台运行；只有任务里完全没有写操作（纯查询）时才考虑后台。

### 3. 一个问题一个子代理

子代理之间没有共享上下文。如果把同一问题拆给多个子代理，要么主代理拼命转述削弱分工意义，要么子代理独立排查重复浪费上下文。

**决策**：一个问题对应一个子代理，包揽该问题所有相关文件改动。N 个独立问题 = N 个子代理串行。

### 4. 子代理只反馈"修改要点"

如果让子代理顺手写项目汇总 / 长期文档，会出现风格不一致、时间线顺序不符合用户叙事结构、视角局限等问题。

**决策**：子代理只反馈结构化要点（文件清单、编译验证结果、偏离方案点、遗留项），汇总 / 长期文档由主代理统一组织语言。

### 5. 提示词必须包含"已确认方案"，不必赘述项目级规范

子代理冷启动，没有主对话的上下文。如果只给问题描述让子代理自己判断怎么改，会偏离用户已确认的方案细节、重复根因排查、命名 / 风格各自为政。

**决策**：子代理提示词必须包含主代理与用户已对齐的方案细节，以及范围约束。项目级规范子代理会自行从 CLAUDE.md 获取。

### 6. 编译 / 测试验证归子代理，主代理不重复跑

主代理在收尾时再跑一次编译 / 测试，等于把已知通过的工作又做一遍，浪费上下文且增加工具调用噪声。

**决策**：实现子代理自跑编译；测试子代理自跑测试套件。主代理只整合各子代理的输出，不重复执行验证。

### 7. 补充测试循环

实现子代理完成后，主代理询问用户"是否要进行补充测试？"。同意后，给每个实现代理配一个测试代理（一一对应）：

- 测试代理评估"原有单元测试是否失去意义 / 需调整、是否应该增加新的测试"
- 跑必要测试（含跨模块测试）
- 把暴露的业务代码问题反馈给主代理；主代理派给对应的实现代理修复
- 修完后让测试代理复验
- 每对 F-V 完整闭环后才进入下一对，保持严格串行

**平台差异**：

| | Claude Code | Codex |
|---|---|---|
| 通信工具 | `SendMessage`（需 Agent Teams 实验功能） | `send_input`（原生工具） |
| 可用性 | 需启用 `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1` | 始终可用 |

### 8. 实现代理 / 测试代理职责按文件归属分

业务代码改动派给实现代理；测试代码改动派给测试代理。两类代理不交叉。

**理由**：角色清晰，prompt 不必涉及对方领域细节；主代理按文件归属派任务，分工边界自然清晰。

### 9. Codex 版适配

Codex 版与 Claude Code 版核心工作流完全一致，差异仅在于平台工具名和子代理通信机制：

| 方面 | Claude Code | Codex |
|------|------------|-------|
| 派生子代理 | `Agent` 工具 | `spawn_agent` + `wait_agent` |
| 回复子代理 | `SendMessage`（实验功能） | `send_input`（原生工具） |
| 子代理身份传递 | prompt 中声明角色 | 同左（Codex 子代理无法通过运行时字段自省身份） |
| 并行/后台权限 bug | 存在（#57037, #34095） | 不存在 |
| skill 目录 | `~/.claude/skills/` | `~/.codex/skills/` |
| UI 元数据 | 无 | `agents/openai.yaml` |
| 隐式触发控制 | 由 description 约束 | `policy.allow_implicit_invocation: false` 硬关闭 |

**决策**：保持两份 SKILL.md 各自维护（而非一份共用），因为工具名差异贯穿全文（核心原则、工作流、模板、诊断信号），共用反而增加条件分支和阅读负担。三份 references 内容基本一致（仅路径和工具名不同），也各自维护以保持子代理读取路径的简洁性。

## 三层职责分工（description / SKILL.md / README）

skill 的内容按"谁读"划分三层职责（两版通用）：

| 层 | 职责 | 内容范围 |
|---|---|---|
| description | 让 AI 判断能不能用 | 触发约束 + 一句话定位 |
| SKILL.md 正文 | AI 用了之后怎么执行 | 核心原则 + 5 阶段工作流 + 何时即便已触发也直接改 |
| README | 给用户的项目介绍 + 环境说明 | 解决的问题、流程示意、环境配置、安装、触发说明 |

Codex 版额外增加 `agents/openai.yaml` 作为 UI 层的元数据（display_name、short_description、brand_color、default_prompt、policy）。

## 触发判断

**仅主动触发**。本技能改变主代理的默认协作模式（影响是否下场写代码、是否串行分发子代理），如果根据任务表象自行启用，会出现以下副作用：

- 用户原本期望主代理直接改的小任务，被多绕一道"分发-子代理-反馈-整理"流程，反而慢
- 用户在多步任务里习惯主代理边读边改、随时打断调整方向；技能化分发后主代理在子代理跑动期间不可中断，打乱节奏
- 不同项目对"主代理 vs 子代理"边界的偏好不同；自动触发等于强加一种默认

因此把触发权完全交给用户：

- 用户显式调用 `/plan-then-delegate`（Claude Code）/ `$plan-then-delegate`（Codex）
- 用户在自然语言里明文提到本技能名 / 工作流
- 项目 CLAUDE.md / 项目记忆里声明默认采用本工作流

主代理**不要**根据"多文件 / 多问题 / 看起来复杂"自行启用。

Codex 版额外在 `agents/openai.yaml` 中设置 `allow_implicit_invocation: false`，从平台层面阻止自动注入，确保仅手动触发。

启用后何时仍由主代理直接改（不分发）：

- 单个简单改动（一行 typo、一个变量重命名）
- 用户明确"这次你直接改"
- 纯研究 / 探索任务

## 诊断信号

### Claude Code：权限拒绝

子代理返回里出现：

```
Permission to use Write/Edit/Bash has been denied.
... Let the user decide how to proceed.
```

这是 Claude Code 父子权限传递 bug 的标准文案。处理顺序：

1. 检查本次是不是并行 spawn → 改串行
2. 检查 `run_in_background=true` → 改前台
3. 检查 `~/.claude/settings.local.json` 的 `permissions.allow` 是否包含子代理需要的工具规则
4. 仍失败：跟用户说明本次例外由主代理直接落盘，后续仍走子代理

### Codex：子代理角色偏离

如果子代理返回的内容偏离分配的角色（实现代理改测试、测试代理动业务代码），说明子代理未正确识别自身角色。Codex 子代理无法通过运行时字段可靠自省身份，依赖 prompt 中的角色声明。

处理：用 `send_input` 重新发送角色声明 + 范围约束，让子代理纠正。

### 通用：「references 读取失败」

子代理读不到执行规则文件。通常因为 skill 没完整安装：只链了 SKILL.md 单文件，没把 references/ 目录一起带过来。

处理：告知用户「plan-then-delegate skill 未完整安装，references 目录缺失」，让用户修复后重试。

## 起源

本技能源于一次实战发现：尝试让主代理并行 / 后台分发子代理时，命中 Claude Code 已知的父子权限传递 bug（#57037、#34095），子代理 Write/Edit 全被拒。改为单独前台依次起后，子代理顺利落盘。从这次场景开始抽象成技能，并在后续迭代中扩展出"编译 / 测试验证归子代理"（决策 6）和"补充测试循环"（决策 7）。

Codex 版改编于 2026-05-22。Codex 的三个特性（子代理直接向用户发消息、原生支持重载子代理、身份由主代理传递）天然契合本技能的工作流，尤其是补充测试循环不再依赖实验功能开关。
